# Solution design: AI-assisted testing for system migrations

Nov 17, 2026 · @Jorge Nascimento

## Vision and objectives

The solution uses AI to generate, validate and maintain automated tests in the consultancy's migration services, replacing today's manual test design and automation.

Today all testing is manual, with no framework and no CI. Clients migrate legacy systems (COBOL, PHP, Node.js, Python, Java) to varied targets, and every migration has to prove that behavior was preserved.

Objectives:

- Generate test cases and automatable scenarios from the markdown specs, without relying on someone to write them by hand.
- Verify equivalence between legacy and target by comparing behavior directly.
- Deliver tests that run on the client's GitHub Actions, without depending on our tool.
- Reduce the effort of maintaining tests and analyzing failures.

Out of scope: selling the tool as a product, replacing human exploratory testing, and covering non-functional requirements such as performance and security in depth.

## Context and assumptions

The design rests on the team's answers and on the analysis of a real spec, the SEARCH-EXAMPLE example.

| Topic | Assumption |
| --- | --- |

| Target | Varies by client, with several languages and frameworks |

| Jira | Tickets only, with no test-management plugin |

| Team | Most do not program; a small group does |
| Legacy-to-target interface | Mapping defined by the migration team |
| Systems tested | Web and APIs, plus console and batch in migrations |

The spec is an AI's interpretation of the legacy behavior, not the original business intent. This affects what serves as the test oracle, as the following sections explain.

## Design principles

Efficiency comes from where AI enters and how its output is verified, not from using more AI.

1. **AI generates, deterministic code executes.** Tests are code that runs predictably in CI. AI is used to create, maintain and analyze, never on the critical path of execution.
2. **The spec is read-only.** The test tool writes nothing to it. Regeneration by STC would erase anything outside the `stc:manual` blocks, and those blocks take precedence over the text, so they would change what the implementer receives. The test tool consumes the spec only through the contract: the markdown, the sidecar and STC's read-only MCP tools.
3. **The oracle is the legacy behavior.** The spec is an AI interpretation and may be wrong. The old program, when executable, is the strongest reference.
4. **Separate contexts.** Whoever designs the cases does not see the target code, enforced by folder permissions. This reduces the risk of spec, code and tests all being wrong in the same way.
5. **Ask instead of guessing.** What the spec does not define becomes a question for a person, never an assumption by the AI.
6. **Humans approve.** The QA analyst approves scenarios, the automation engineer approves new code and the migration team approves the interface mapping.
7. **Delivery without dependency.** The delivered tests run on the client's GitHub Actions without our tool.

## Spec reader and gap triage

STC emits a structured sidecar next to every feature spec, and the test tool reads it instead of parsing markdown. A triage step then separates real gaps from false ones.

**Where the work is done.** The test tool is a separate application, a sibling directory of STC in the same repository. The only shared surface is the contract in `contracts/` (a JSON Schema plus fixtures). STC validates its own output against it and the test tool validates its input against it, so a change to the contract runs the checks of both sides. The test tool reads STC and never the other way around.

**Sidecar emitted by STC** (`features/<slug>.spec.json`, schema `stc.spec-sidecar/1`; the new requirements go in the specification section of STC's functional spec)

- Each item (requirement, rule, acceptance scenario, interface, data, task, risk) has an ID such as `program-search-example/FR-04`, the text hash (`text_sha256`), confidence, verified `file:lines` citations, an origin (`generated` or `manual`) and a status against the previous generation (`new`, `unchanged`, `changed`).
- Acceptance scenarios carry structured Given/When/Then fields. This needs the generation prompt to ask for them, which regenerates the specs once.
- The sidecar pins the version by the legacy code version, the stack hash and the page's input hash, and lists blocks of `stc:manual` by key and hash.
- It is written next to the specs, so `stc spec --output` carries it along.

**IDs are never reused.** Position-based IDs would break when a regeneration inserts an item in the middle. On regeneration, a new item is matched to an old one first by the same text hash, then by the same set of citations (same evidence with a different text is `changed` and keeps its ID). An unmatched new item gets the next free number and an unmatched old one goes to `retired`. While the inputs do not change, the page is not regenerated and the IDs stay identical.

**Reader (in the test tool)**

- Deterministic, with no LLM: it validates the sidecar against the contract and refuses an unknown major version of the schema instead of generating tests over a format it does not understand.
- Stores its own state outside the spec. On each regeneration it reads the `status` and the text hash: `changed` and `retired` items mark the affected tests as "to review" or obsolete.
- Warns when the format changes between tool versions or between source languages.
- Answers to real questions only enter the spec by decision of the spec process owner, in an `stc:manual` block. The reader takes those items with precedence (origin `manual`).

**Gap triage.** Each item under "Gaps" is classified as resolved elsewhere, real question or out of scope. Each section was generated with partial context, so many gaps ask what another section already answers. The work is split:

- STC cross-checks each gap against the text of the other sections of the same spec (one LLM pass per page, with no code) and records `answered_elsewhere` with the IDs that answer it, or `open`. This also improves the spec for anyone who never uses tests.
- The test tool and the migration team decide the rest: real question or out of scope.

**Findings in the example spec (SEARCH-EXAMPLE)**

| Finding | Where | Handling |
| --- | --- | --- |
| The requirements say "blank line" and the acceptance scenarios say "a space" for the same `DISPLAY` | Functional requirements vs Acceptance scenarios | Decide by the legacy behavior |
| Gap "what records does SETUP-TEST-DATA provide" | Acceptance and Risks, answered in requirements 1 and 2 | Resolved elsewhere |
| Gap "what output does DISPLAY-FOUND-ITEM produce" | Acceptance and Risks, answered in requirement 5 | Resolved elsewhere |
| Gap "how are idx and idx-2 initialized" | Data, answered in requirements 4 and 9 | Resolved elsewhere |
| Invalid or short input in `PIC 9(4)` fields | Several sections | Real question, settled by the legacy |
| Selection rule with duplicate keys | Risks | Real question |
| `SEARCH ALL` semantics with ascending and descending keys | Risks | Real question |
| REST contract (fields, states, errors) and console transcript vs structured result | Interfaces and Proposed design | Decide in the interface mapping |
| REST design with medium confidence | Proposed design | Not an oracle until confirmed |

## Oracle hierarchy and differential testing

In a migration, a test's expected result comes from three sources, in order of confidence.

1. **Legacy behavior at runtime.** It is the strongest reference. When the old program is executable in a test container (PHP, Node.js, Python and Java), the same inputs run on the legacy and on the target and the outputs are compared. COBOL programs are never executed: the tool does not run COBOL in any form, so this source has no runtime oracle.
2. **Manual corrections** in the spec's `stc:manual` blocks, which the spec itself declares take precedence.
3. **The spec text**, useful but not infallible, because it is an AI-generated interpretation.

When the sources disagree, the higher-confidence one wins and the divergence is recorded as a finding. A spec error detected this way improves the implementation, not just the tests.

**Differential comparison**

- **Normalization:** timestamps, generated identifiers, collection order, whitespace and padding are ignored or normalized, with per-program tolerances defined in the interface mapping.
- **Classifying differences:** migration error, legacy bug the team decided not to preserve, nondeterminism or spec error. Every unexplained difference goes to human triage.
- **Capturing real traffic** on the legacy (PHP, Node.js, Java with HTTP), anonymized and replayed on the target. It gives realistic coverage no spec provides, but needs care with personal data.
- **Without an executable legacy,** which is always the case for COBOL, tests rely only on the spec and the manual corrections, and reports flag the lower confidence.

**Migration pitfalls catalog.** The agent that designs the cases uses a catalog per source language to generate the edge cases where migrations usually fail.

| Source | Typical interface | Running the legacy | Pitfalls |
| --- | --- | --- | --- |
| COBOL | Console, batch, fixed-width files | Not executed | Numeric `PIC`, padding and truncation, encoding, rounding |
| PHP | Web with forms and sessions, APIs | Easy, in a container | Weak typing and implicit conversions, dates and time zones, HTML escaping |
| Node.js | APIs, async services | Easy | Floating-point numbers, `null` vs `undefined`, event ordering |
| Python | Scripts, APIs, data processing | Easy | Precision (`int` vs `Decimal`), text encoding, sorting and locale |
| Java | APIs, batch | Easy | `BigDecimal` and rounding, framework versions, serialization |

## Adapters and interface mapping

Tests run at the system's observable boundary, so they depend on neither the legacy language nor the target's. Two kinds of adapter connect the tool to both sides.

- **Legacy adapter:** knows how to build and run the old system in a test container and capture its behavior. It varies by source language and does not exist for COBOL, which is never executed.
- **Target adapter:** knows how to start the new implementation and call its interface. The client must provide that interface's contract, for example an OpenAPI.
- **Boundary adapters** in the core: HTTP, web UI, console and files, and database to compare state.

The tool keeps a single test stack for every client. Unit tests in the target's language stay outside the core, as an optional module.

**Interface mapping file.** When the legacy and the target have different interfaces, such as COBOL's console and the target's REST, someone has to say what corresponds to what. The migration team defines this per program, in a versioned, approved file, with:

- **Legacy invocation:** how to run the program (sequence of console inputs, HTTP call, arguments).
- **Target invocation:** corresponding endpoint and fields. In the SEARCH-EXAMPLE case, the five prompt inputs become the five fields of `POST /program-search-example/runs`.
- **What to compare:** structured results or the full console transcript, which is a real gap in the example spec.
- **Normalization rules** for the comparison.
- **Accepted differences:** divergences decided on purpose, with justification.

The AI proposes a draft from the spec and the legacy code, and the migration team approves. If the same team defines the mapping and implements, an error in the mapping contaminates both ends, so decisions are recorded and visible in review. Until an approved mapping exists, contract-level tests stay pending.

## Gherkin scenarios and action library

Tests are Gherkin scenarios in business language, bound to a curated action library, so that people who do not program can read and approve them.

**Structured case.** In the design phase, each case has an intermediate format with: stable ID, title, origin, traceability (IDs derived from the spec and Jira tickets), type (API, web, console or hybrid), priority, preconditions, data by reference, steps with expected result, status, doubts and provenance (model, prompt version, who approved). Status follows: draft, in review, approved, automated, stable (passed N consecutive runs) and obsolete. Once approved, the Gherkin scenario in Git becomes the single source.

**Example scenario** (from requirement 7 of the example spec):

```gherkin
# language: en
@SEARCH-EXAMPLE/FR-07 @TC-0007 @priority:high
Feature: Keyed table search

  Scenario: Three ids where one differs find no record
    Given the program SEARCH-EXAMPLE is ready with the test data
    When I search the keyed table for the ids "0001", "0101" and "0499"
    Then the result is "Item not found."
```

**Cases safely derived from the example spec**

| Case | Input | Expected | Source |
| --- | --- | --- | --- |
| Hit on the 1st search | id-1 = 0002 | Record with ids 0002, 0102, 0499 and name "test item 2" | FR-4, FR-5 |
| Miss on the 1st search | id-1 = 0004 | "Item not found." | FR-4 |
| Three ids correct | 0003, 0103, 0498 | Record 3 | FR-7 |
| Three ids, one differs | 0001, 0101, 0499 | "Item not found." | FR-7 |
| Sequential on an unordered table | id = 1 | "Value of id 1." (3rd position) | FR-2, FR-9 |
| Sequential, miss | id = 4 | "Item not found." | FR-9 |

**Linter rules**, which run before any PR is accepted:

- Every scenario has a traceability tag and a case ID.
- Every scenario has at least one `Then` step with a real assertion.
- Steps stay at business level, with no selectors, URLs or technical values in the text.
- Data always comes by reference to named datasets.
- Scenarios are independent, with no order dependence, and clean up their data at the end.
- Every step exists in the action catalog.

**Action library in three layers**

| Layer | Content | Maintained by |
| --- | --- | --- |
| Core | Generic actions: HTTP request, validate status and JSON, navigate, click by role or label, fill, validate text, send input to the console, compare files and database state | The platform, reused across all clients |
| Client domain | Business actions, such as "log in" or "add product to cart", with page objects and API clients | Automation engineers, per client |
| Data | Versioned datasets, data generators, credentials via GitHub Secrets | Team and client |

Principles: semantic locators (role, label, test-id) instead of fragile XPath, and each action with a signature and a natural-language description. A generator creates `actions.json` from the code (the `@Action` annotation of each step definition), a test fails when it is out of date, and the linter rejects a step that matches no action in it, and the AI only binds steps to actions that exist in it.

**When an action is missing,** the AI records the gap, drafts an implementation proposal and opens a separate PR for an automation engineer to review. New code is rare, small and always reviewed by someone who programs.

## Technical stack and CI

The tool uses a single test stack for all clients, with execution on the client's GitHub Actions.

**Stack (decided):** Cucumber-JVM, Playwright (Java), REST Assured and JUnit 5, in a single Java project. Java is the language the group that programs already knows (confirmed), there is one language for API, web, database and files, and Cucumber-JVM is the reference implementation of Gherkin with mature reports (Allure). The pilot is API and file testing (a COBOL console program behind REST and a PHP or Node.js program over HTTP), where REST Assured and JDBC fit well. The cost is that Playwright in Java has fewer examples than the TypeScript version, which matters when web tests enter. Because the scenarios are Gherkin and the steps only bind them to actions, the web part can be revisited then (for example with `playwright-bdd`) without rewriting the scenarios.

**Two layers.** What runs on the client's GitHub Actions is Java and needs nothing of ours: the tests, the scenario linter and the generator of `actions.json` live in the Java project, so `validate-scenarios` runs without our tool. What the consultancy runs is a separate tool in Python, next to STC: it reads the sidecar, triages the gaps, designs the cases, drafts the interface mapping and opens the pull requests. It cannot import STC, so it has its own minimal LLM client (one call with a JSON Schema reply); that small duplication is accepted to keep the two independent.

```
stc-tests/
  tool/       # Python: reader, agents, mapping, pull requests
  template/   # Java project delivered to the client: actions, linter, caller workflows
```

**Test repository**

```
test-repo/
  features/
    api/
    web/
    console/
  src/test/java/.../
    actions/core/
    actions/domain/
    hooks/
  data/
  catalog/actions.json       # generated
  mapping/                   # interface mapping per program
  .github/workflows/         # calls the reusable workflows
```

**Command line and folders.** The test tool is a separate application (a sibling directory of STC in the same repository) with its own CLI and no frontend in the pilot, following STC's convention for folders:

| Option | Meaning | Default |
| --- | --- | --- |
| `--specs <dir>` | Where to read the specs and their sidecar files. Must be the same folder used in `stc spec --output`. | `STC_SPECS` |
| `--output <dir>` | Where to write cases, Gherkin scenarios, mapping and reports, typically the client's test repository. | `STC_TESTS` |

- A new output folder starts from scratch, because the approval state (status, who approved, prompt version) lives in it.
- An approved scenario versioned in Git is never overwritten. Regeneration only creates new drafts and marks existing cases "to review" when the `text_sha256` of their source item changes. Overwriting requires an explicit `--force`.

**Client GitHub Actions**

GitHub Actions runs only deterministic code: no LLM, no STC and no test tool. Everything that uses AI runs in the consultancy's environment and reaches the client as a pull request.

| Piece | Where it lives |
| --- | --- |
| Caller workflows, a few lines with parameters | The client's test repository (`.github/workflows/`) |
| Reusable workflows (`workflow_call`) | A central repository maintained by the consultancy |
| Secrets and environments | The client's Secrets and Environments |

| Workflow | Trigger | What it does |
| --- | --- | --- |
| `validate-scenarios` | PR touching `features/`, `catalog/` or `mapping/` | Linter: traceability tag, a real assertion in `Then`, business-level steps only, data by reference, every step exists in `actions.json`. Fast, with no test environment. |
| `test-pr` | PR | Runs the approved and stable scenarios against the test environment. |
| `test-nightly` | Schedule | Full suite, including scenarios not yet stable. Repeats runs to measure flakiness and counts consecutive green runs (the `stable` status). |
| `test-on-demand` | `workflow_dispatch` | Runs one tag, feature or requirement. |
| `differential` | Schedule and on demand | Starts the legacy and the target, runs the same inputs and compares them with the normalization of the interface mapping. Only for executable legacies, never COBOL. |
| `hidden-suite` | PR and schedule | Hidden subset, to detect overfitting of the implementation to the visible tests. |

Steps of a typical run:

1. Checkout and setup (Java, Maven or Gradle cache, Playwright browsers).
2. Start the target, or point to the existing environment, and wait for its health check.
3. Run Cucumber with the chosen tag.
4. Publish the report (Playwright HTML or Allure), traces and failure captures as artifacts.
5. Report to Jira: a summary comment on the requirement's ticket.

Inputs and secrets:

- Parameters: target environment, tag, client profile and workflow version.
- Test credentials, the Jira token (limited permissions) and, if used, access to the hidden suite are in the client's Secrets and Environments, never in repository files or in the model's context.
- If the test environments are only reachable inside the client's network, CI uses self-hosted runners. This is still to be confirmed.

What does not run in Actions: case design, Gherkin generation, binding to actions and the interface mapping draft (consultancy); failure triage (AI and people, outside CI); the sidecar reader and STC.

Defects are not opened by the run: the failure is classified first (bug, outdated spec or incorrect test), so the run only comments the summary and attaches the report, and a defect is created after triage or with a "to triage" label.

**Validating generated tests.** For black-box tests, code mutation (PIT) does not apply. We use:

- Repeated execution (5 to 10 times) to detect flakiness before accepting the test.
- Assertion sensitivity testing: we deliberately change the expected value or the input and confirm the test fails.
- Automatic check that every scenario has real assertions and traceability to a requirement.
- Differential comparison with the legacy, when executable.
- QA analyst review of whether the scenario reflects the expected business behavior.

## Roles and workflow

Most of the team does not program, so the workflow puts decisions in readable scenarios and only calls in programmers when there is new code.

| Role | Responsibility |
| --- | --- |
| QA analyst (most of the team) | Answers the doubts, approves scenarios and analyzes results |
| Automation engineer (small group) | Maintains the action library, reviews new code and configures CI |
| Migration team | Defines and approves the interface mapping and decides the real spec gaps |
| Platform owner | Client profiles, governance, metrics and the tool's evolution |

**No frontend in the pilot.** Review happens where the team already works: QA approves cases in Jira, the automation engineer approves code in pull requests, the migration team edits the mapping file and the `stc:manual` blocks, and results come from the CI report and Jira. The test tool offers only its CLI and files. Whether a thin review screen is worth building (only what needs a decision, with approve or reject and a reason, writing to the test repository and never replacing it) is evaluated after the pilot, based on the case rejection rate and the effort of reviewing in Jira and Git.

**Git and Jira.** The client's Git holds the scenarios, the action library and the code, with versioning and PR review. Jira, which only has tickets, serves for traceability:

- Requirements and stories linked to scenarios by the ticket ID in a tag.
- Status of each case, through a "Test Case" ticket type or a standard label, to be agreed per project.
- Defects created after triage, when a failure is classified as a real bug, linked to the requirement. The CI run itself only comments a summary on the ticket (see "Client GitHub Actions"); creating the defect at once with a "to triage" label is an open decision.
- A summary of each run, as a comment on the relevant ticket.
- A Jira API token with limited permissions.

Existing Excel files serve only as an import source for clients who already have written cases. Once imported, they are no longer maintained.

**Workflow per migrated program**

1. The spec is generated and pinned by version, with its sidecar. The reader validates the sidecar and takes the requirements and gaps from it.
2. The migration team resolves the real gaps and approves the interface mapping.
3. The AI designs the cases from the spec, without seeing the target code. The QA analyst approves in Jira.
4. The AI writes the Gherkin scenarios and binds the steps to the action library.
5. The validator runs, repeats and tests the sensitivity of the assertions.
6. The automation engineer approves the PR, which only has new code when an action is missing.
7. The client's CI runs the tests and, when possible, compares with the legacy.
8. Triage classifies failures as bug, outdated spec or incorrect test, and reports to Jira.

Approved tests are visible to the implementer as a TDD target. A hidden subset runs only in CI, to detect overfitting to the visible tests.

## Governance and security

Clients accept code going through an LLM API, but the consultancy remains responsible for containing what leaves the client's environment.

- **Contract with the LLM provider:** zero data retention and no training on client content, formalized by contract or DPA. The provider and terms are still to be decided.
- **Masking** of secrets, credentials and personal data before sending any content to the model, including traffic captured from the legacy.
- **Isolation per client:** context, data, credentials and profiles never mix across projects, and each client has its own project profile.
- **Least privilege per agent:** the case-design agent only reads the spec. The agent that binds to actions sees the target code but does not change the approved expected result.
- **Audit:** record of what the AI generated (model, prompt version, inputs) and who approved each step.
- **Mandatory human approval** before any test enters the client's repository.
- **Test credentials** kept only in the client's GitHub Secrets, never in repository files or the model's context.
- **Real legacy traffic:** only captured with the client's authorization and after anonymization.

## Metrics

Line coverage misleads, so we measure how useful the tests are and the gain from the service. Numeric targets are to be defined after the pilot.

| Metric | What it measures |
| --- | --- |
| Requirement coverage | Spec requirements with at least one approved case, and critical requirements with several |
| Case approval rate | Cases approved without correction by the analyst, and reasons for rejection |
| Assertion sensitivity | How many tests fail when the expected value is deliberately changed |
| Injected defects detected | Known bugs placed in a test environment that the tests catch |
| Divergences found | Differences between spec, legacy and target, and how many were real bugs |
| Flakiness rate | Tests that fail intermittently across repeated runs |
| False gap rate | Spec gaps classified as resolved elsewhere |
| Time per automated case | Hours to automate a case, manually and with the tool |
| Escaped defects | Bugs found in production that the tests should have caught |
| Cost per useful test | AI and review cost per test that stayed in the repository |

## Risks and mitigations

The biggest risk is tests confirming an error instead of detecting it, because spec, code and tests all come from AI.

| Risk | Mitigation |
| --- | --- |
| Spec, code and tests are wrong in the same way | Separate contexts through permissions, hidden tests in CI, comparison with the legacy and a divergence report |
| The AI-generated spec describes the legacy wrongly | Audit the `file:lines` citations against the code and run the legacy as the oracle |
| Legacy not executable | Tests only from the spec and manual corrections, with the lower confidence flagged in reports |
| Wrong interface mapping, defined by the same team that implements | Decisions recorded and visible in review, and the AI proposing the draft |
| False gaps flood the analyst with questions | Triage that cross-checks each gap against the other sections before asking |
| Format change or spec regeneration invalidates the tests | Read-only spec, versioned sidecar contract checked by both sides, IDs that are never reused, drift detection through `status` and text hash |
| Spec format differs across source languages | Validate the reader with real PHP, Node.js and Python samples before the pilot |
| Reviewer approves without reading | Show only what needs a decision (doubts, divergences, scenarios without spec support) and measure the rejection rate |
| Flaky tests | Repeated execution before accepting and semantic locators |
| Production data or secrets sent to the LLM | Masking, anonymization, DPA and least privilege per agent |
| Test environments inaccessible or unstable | Confirm access and controlled data before each pilot, and self-hosted runners if needed |
| Unwritten business rules | Human exploratory testing continues to exist |

## Pilot and roadmap

The pilot proves the pipeline on two programs from different source languages before any expansion.

&#91;embedded content: roadmap · 5 phases and 2 gates\]

The phases are not to scale and have no dates, which depend on the team and the pilot client.

The pilot uses the COBOL example (SEARCH-EXAMPLE, from console to REST) and a program in another language with an HTTP interface, preferably PHP or Node.js. Both run the flow: spec reader, gap triage, interface mapping, approved cases, execution on the client's GitHub Actions and a report in Jira. Only the non-COBOL program is compared with the running legacy; the COBOL program is tested from the spec and the manual corrections.

It measures requirement coverage, case approval rate, divergences found, injected defects detected, stability and time per case. Numeric targets are to be defined before starting.
