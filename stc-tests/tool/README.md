# stc-tests tool

The consultancy-side tool of the test solution: reads the specifications `stc spec` writes (through
the contract in `contracts/`), validates them and tracks what changed between runs.

```bash
uv sync
uv run stc-tests check --all --specs ../../specs-out        # validate against the contract
uv run stc-tests ingest APP --specs DIR --output DIR [--dry-run]   # new / changed / retired
uv run stc-tests scenarios APP --specs DIR --output DIR --catalog PATH/actions.json [--force|--dry-run]
uv run ruff check . && uv run ruff format --check . && uv run mypy && uv run pytest
```

`--specs` defaults to `STC_SPECS` (else `./specs`), `--output` to `STC_TESTS` (else `./testsuites`).
It never imports `stc`; `tests/test_independence.py` enforces it.

## Drafting scenarios

`scenarios` asks a model for Gherkin scenarios of each feature, bound to the action catalog
(`catalog/actions.json`, generated by the Java template). The model proposes; the code keeps a
scenario only if every item it covers exists in the specification, every step matches an action of
the catalog and it has a `Then`. A step with no action is reported as a missing action. Case IDs
(`TC-0001`) are assigned by the tool and never reused; a case whose source item changed is listed as
"to review".

Drafts go to `OUTPUT/<application>/features/<feature>.feature`. A file that already exists is never
overwritten: the new draft goes to `<feature>.proposed.feature` unless `--force` is given.
`--dry-run` builds the prompts and calls no model.

The model is configured by `STC_TESTS_LLM_MODEL`, `OPENAI_API_KEY` and (optionally)
`OPENAI_BASE_URL`, from the environment or from a file given to `--env-file` (or `STC_ENV_FILE`;
variables already set win, and values are never printed), as in `uv run stc-tests --env-file ../../.env scenarios ...`; the client is the small one in `llm.py` (one call, a JSON Schema reply). Prompts
carry specification text: use real specifications only under the terms agreed with the client.
Step matching in the tool supports `{string}`, `{int}`, `{float}`, `{word}` and `{}`.

## Human approval

A person decides which drafts become tests; the tool only records it.

```bash
uv run stc-tests review APP --specs DIR --output DIR            # status of every case
uv run stc-tests approve APP TC-0001 TC-0002 --by "Name" --output DIR   # or --all-drafts
uv run stc-tests reject APP TC-0003 --by "Name" --reason "why" --output DIR
```

- `approve` adds `@status:approved` to the scenario in the feature file and records who, when, the
  model, the prompt version and a fingerprint of the approved text in `cases.json`.
- `reject` removes the scenario from the file and keeps the reason (it feeds the approval-rate
  metric); the same case is not proposed again.
- A case goes back to **to review** (and loses its tag the next time the file is written) when its
  text changes after approval or when the text of a specification item it covers changes.
- The tool never writes steps into an approved scenario; regeneration only proposes
  (`<feature>.proposed.feature`) unless `--force` is given.

## Interface mapping

```bash
uv run stc-tests mapping APP --specs DIR --output DIR [--force|--dry-run]   # draft, for the migration team
uv run stc-tests approve-mapping APP PROGRAM --by "Name" --output DIR
```

`mapping` writes `OUTPUT/<application>/mapping/<program>.mapping.yaml` (the format is
`contracts/interface-mapping.schema.json`). The model proposes the inputs, the request and the result
paths; the code builds the file, always adds the question of confirming the names against the target's
contract and leaves `accepted_differences` empty. An existing file is never overwritten (the new draft goes to
`<program>.proposed.mapping.yaml` unless `--force`). `approve-mapping` refuses until the open
questions are removed by editing the file, then sets `status: approved`, who and when, keeping your
comments.
