# stc-tests tool

The consultancy-side tool of the test solution: reads the specifications `stc spec` writes (through
the contract in `contracts/`), validates them and tracks what changed between runs.

```bash
uv sync
uv run stc-tests check --all --specs ../../specs-out        # validate against the contract
uv run stc-tests ingest APP --specs DIR --output DIR [--dry-run]   # new / changed / retired
uv run stc-tests scenarios APP --specs DIR --output DIR --catalog PATH/actions.json [--force|--dry-run]
uv run ruff check . && uv run ruff format --check . && uv run mypy && uv run pytest
```

`--specs` defaults to `STC_SPECS` (else `./specs`), `--output` to `STC_TESTS` (else `./testsuites`).
It never imports `stc`; `tests/test_independence.py` enforces it.

## Drafting scenarios

`scenarios` asks a model for Gherkin scenarios of each feature, bound to the action catalog
(`catalog/actions.json`, generated by the Java template). The model proposes; the code keeps a
scenario only if every item it covers exists in the specification, every step matches an action of
the catalog and it has a `Then`. A step with no action is reported as a missing action. Case IDs
(`TC-0001`) are assigned by the tool and never reused; a case whose source item changed is listed as
"to review".

Drafts go to `OUTPUT/<application>/features/<feature>.feature`. A file that already exists is never
overwritten: the new draft goes to `<feature>.proposed.feature` unless `--force` is given.
`--dry-run` builds the prompts and calls no model.

The model is configured by `STC_TESTS_LLM_MODEL`, `OPENAI_API_KEY` and (optionally)
`OPENAI_BASE_URL`; the client is the small one in `llm.py` (one call, a JSON Schema reply). Prompts
carry specification text: use real specifications only under the terms agreed with the client.
Step matching in the tool supports `{string}`, `{int}`, `{float}`, `{word}` and `{}`.
